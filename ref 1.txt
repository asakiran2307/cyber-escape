Main problems in the current version
Station 2 is too easy — the password is directly visible from the clues.
Station 3 is too obvious — .edu immediately gives away the answer.
Station 4 is only a memory quiz, rather than a final investigation.
The same fixed passcodes mean teams can simply share answers.
The “real email” approach teaches that a correct domain = safe, which isn't always true.
A real person's name should not be used for the password-guessing challenge.
The flow is Read → MCQ → Passcode, rather than an actual investigation.

I would upgrade it to:

OBSERVE → QUESTION → DOUBT → VERIFY → CONNECT → DECODE → ESCAPE

🕵️ STATION 01 — THE EMAIL THAT SHOULD NOT EXIST

Instead of asking:

Which email is genuine?

Give them three pieces of evidence.

Email A

From: library@university.edu
Subject: Your library transaction

Your book Network Security Basics was returned successfully.
Transaction ID: LIB-4481.

Email B

From: library-support@university-help.example
Subject: URGENT — Account Suspension

Your library account will be permanently deleted in 15 minutes.
Click here immediately to prevent suspension.

Email C

From: security@university.edu
Subject: Password Verification Required

Reply to this email with your current password and OTP to verify your identity.

Now ask:

Question 1

Which message contains the most dangerous request, even though the sender appears to use the university domain?

A. A
B. B
C. C

Answer: C

That's much better because students learn:

A correct-looking domain does not automatically make a request safe.

Question 2

Which two clues should immediately increase suspicion?

Urgency
Password request
Transaction number
Normal notification

Answer: Urgency + Password request.

Final extraction

Give each correct answer a number:

C = 3
Urgency = 7
Password = 4

The station generates:

374

They don't receive a giant obvious passcode like SAFE-PASS-101.

They enter:

374

to unlock Station 2.

🕵️ STATION 02 — THE DIGITAL SHADOW

Do not use a real person's name or ask students to guess an actual person's password.

Create a fictional character:

CASE FILE: NOVA-27

Students discover:

🎮 Gamer
📸 Photography Club
🐕 Dog named Bruno
🎓 Joined campus in 2024
👕 Favourite jersey number: 27
☕ Favourite café: Byte Café

Then give them four possible password patterns:

A. Bruno2024
B. Nova!27
C. Campus#8Q
D. X7!pL9@z

But here's the trick:

Question

Which password demonstrates the highest risk of being predictable from publicly available information?

Answer:

A — Bruno2024

Then give a second clue:

The investigator discovers the person frequently uses the number 27 in public posts.

Now ask:

Which additional information would make the password pattern even more predictable?

A. Bruno
B. 27
C. 2024
D. All three

Answer:

D

Extraction

Instead of revealing the next password directly:

BRUNO = 5 letters
2024 = 4 digits
27 = 2 digits

The system asks:

Take the number of letters in the pet name + the number of digits in the joining year + the jersey number.

Result:

5 + 4 + 27 = 36

Station 2 code:

36

Much more satisfying.

🌐 STATION 03 — THE DOMAIN MIRAGE

This is where you can make it properly tricky.

Don't just give:

Which one has .edu?

Give URLs that look extremely similar.

CASE FILE
A
https://portal.college.edu/exam

B
https://college.edu.login-check.example/exam

C
https://college-exam.example/college.edu/login

D
https://college.edu@secure-login.example/exam

Ask:

Question 1

What is the actual domain in URL B?

Students must identify:

login-check.example

—not college.edu.

Question 2

What does the @ in URL D indicate?

The browser interprets the portion before @ as user-information, while the actual host is:

secure-login.example

Question 3

Which URL actually belongs to the fictional college?

A

Now make the extraction interesting.

A = 14
B = 27
C = 39
D = 52

If the player identifies:

B + D

then:

27 + 52 = 79

Station 3 code:

79
